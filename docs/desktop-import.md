# PC 微信与 QQ 聊天记录

图形界面的 **导入聊天记录** 页面会读取 Windows 的真实“文档”位置，自动发现
`xwechat_files`、`WeChat Files`、`Tencent Files` 内的账号。支持重定向文档目录；
程序没有写死盘符或用户名。应用列表显示来源、账号、路径和识别状态，每行前面有
复选框。自动发现的账号默认不勾选；手动添加的来源默认勾选。检查和导入只处理勾选项。

## 复制与解析

设置独立的资料库目录和工作目录，例如 `E:\ChatArchive\Library` 与
`E:\ChatArchive\Work`。来源可以在其它盘，复制、解密和解析产物都写入指定的工作目录，
合并结果写入资料库目录。程序不会在原始账号目录中建立工作文件。

只复制已识别的聊天数据库及其 WAL/SHM/journal，不扫描收到的任意 `.db` 附件，
也不复制整个客户端缓存。每次复制后校验源文件及副本的完整 SHA-256；如果客户端
同时修改了数据库则保留旧尝试并重新复制。最多重试三次，持续变化时明确报错。
微信/QQ NT 加密库逐页校验 HMAC，合并已提交 WAL 后检查 SQLite 完整性；旧版 QQ
使用独立组件验证密钥及数据库完整性，不声称具有 NT 的页 HMAC。中间副本全部保留，
没有自动清理或删除原件的步骤。

复制、校验、读取密钥、解密、解析消息和阅读器合并分别报告进度。已知总量的阶段
显示字节数、页数或记录数；长步骤定期输出状态。

## 版本与密钥

| 来源 | 当前解析范围 | 加密库的前提 |
| --- | --- | --- |
| PC 微信 4 | `db_storage` 消息分片、联系人；文本、群成员、消息类型和原始字段 | Windows 64 位 Python 可只读检查已登录的 `Weixin.exe` 并验证密钥，也可输入已有密钥 |
| PC 微信 3 | `Msg/Multi/MSG*.db`、`MicroMsg.db` | 需要匹配的已有密钥，或已解密数据库；没有微信 3 自动取密钥功能 |
| QQ NT | `nt_qq/nt_db` 或 `nt_db` 的消息、联系人、群资料；消息体 protobuf；账号内本地媒体匹配 | Windows 64 位 Python 可只读检查已登录的 `QQ.exe` 并验证密钥，也可输入已有密钥 |
| 旧版 QQ | `Msg3.0.db` 的消息表、正文元素、原始字段与媒体引用；独立组件解密 | 需要本地 9.7.23.29348 组件包及匹配的经典 QQ 16 字节密钥；已有明文副本不需要组件或密钥 |

自动发现账号不读取进程。对加密微信 4 / QQ NT 执行检查/导入且没有提供密钥时，才只读检查
运行中的对应客户端；不会启动、注入、暂停或修改客户端，也不保存内存转储。只有通过
本次数据库页 HMAC 验证的密钥才会用于解密。退出登录的账号未必有可用密钥。
QQ NT 的不同加密版本会逐一验证，不能仅凭客户端已登录就判定成功。
同一账号目录同时含 QQ NT 与 `Msg3.0.db` 时，两者分别复制、检查、解析。经典 QQ 与
NT 使用独立消息标识，不根据相似文本、时间或本地序号擅自去重，也不假定旧历史已迁移。
如果其中一个消息库无法解密，已成功读出的部分仍可合并，但任务显示“部分导入”并列出
未导入的数据库。此来源不会被记作全部完成，下次相同来源仍会重试。

设置页支持临时输入密钥或选取已有 JSON 密钥文件。按账号、内部 UID、数据库相对路径
或数据库 salt 索引；微信 4 的不同数据库可能使用不同密钥，不能假定一个 key 通用。
密钥仅传递给本次任务，不写入设置、导入历史、导出数据或日志。

JSON 可使用如下结构（均为示例占位值）：

```json
{
  "wxid_example": {
    "db_storage/message/message_0.db": {"enc_key": "64_HEX_CHARACTERS"},
    "db_storage/contact/contact.db": {"enc_key": "ANOTHER_64_HEX_KEY"}
  },
  "123456789": {
    "nt_qq/nt_db/nt_msg.db": {"passphrase": "EXISTING_NT_PASSPHRASE"},
    "Msg3.0.db": {"legacy_key": "CLASSIC_KEY_32_HEX_CHARACTERS"}
  }
}
```

## 旧版 QQ 本地组件

工具默认从项目 `.work/legacy-qq` 加载组件，或通过环境变量
`CHAT_ARCHIVE_LEGACY_QQ_DIR` 指定目录。目录包含 `legacy-qq-helper.exe`、
`KernelUtil.dll` 及同版本依赖。组件仅保存在本机，不随 Git 提交。
构建与依赖清单见 `native/legacy_qq/README.md`。只有 `KernelUtil.dll` 一个文件不够。

已验证的是 **9.7.23.29348**，按文件 SHA-256 识别，不把其它版本冒充兼容版本。
辅助程序固定为 32 位，与 64 位 GUI 隔离。密钥经匿名管道传入，命令行和日志不包含密钥。
它先制作新的工作副本，再验证、解密；标准化结果通过独立 SQLite 完整性检查后才发布。
错误密钥、组件崩溃、取消操作均保留中间文件，不覆盖原数据库。
仍含非空 WAL/journal 的经典 QQ 快照会明确拒绝，需要客户端正常关闭后的完整快照。

经典 QQ 的自动取密钥尚未实现；安装包和 DLL 本身不含账号密钥，NT 密钥不能截取为
经典密钥。设置页可直接输入 32 位十六进制经典密钥，也可用上述按数据库分开的 JSON。
同一账号只提供经典密钥不会补出其它加密 NT 数据库的密钥。
真实旧库是否可恢复，以匹配密钥后的实际解密结果为准；合成样本通过不等于旧历史已恢复。

微信 4 / QQ NT 的 AES、HMAC、WAL 解密代码位于工具中，使用 Python `cryptography`。
自动取密钥依赖本机正在运行且已登录的对应客户端；有匹配密钥则可离线处理复制出的数据库。
它们不依赖上面的经典 QQ DLL。当前是源码及 Python 运行环境，并非完全自包含的单个 EXE。

## 命令行

```powershell
# 只列出系统文档中的本机账号，不解密，不复制
python -m duoshan_export scan --local --json

# 将发现结果中的一个账号路径复制到 E 盘工作目录后检查
python -m duoshan_export inspect "SOURCE_ACCOUNT_DIRECTORY" --work-dir E:\ChatArchive\Work

# 选定账号导入已有资料库；QQ NT 或离线微信可提供已有密钥文件
python -m duoshan_export import "SOURCE_ACCOUNT_DIRECTORY" -o E:\ChatArchive\Library --work-dir E:\ChatArchive\Work --desktop-keys E:\ChatArchive\private-keys.json
```

PC 入口为统一 `import` 和 GUI；原有 Android 单应用 `export` 接口不变。
`scan --local --inspect --work-dir ...` 会检查所有发现的账号，可能因其中一个账号
缺密钥而中断。需要逐个选择时，使用 GUI 复选框或把具体账号路径传给命令行。

## 阅读器与后续更新

PC 微信目录前缀为 `wxpc_`，QQ 为 `qqpc_`，阅读器分别显示 **PC 微信**、**PC QQ**。
同账号的新快照沿用稳定内部 UID，微信 4 目录尾部安装实例后缀变化不会创建新账号。
有服务器消息 ID 时按会话和服务器 ID 合并；旧历史、备注、正文编辑及隐藏状态保留。
PC 账号与 Android 账号独立，不根据昵称自动合并身份。

QQ 本地媒体恢复不依赖 QQ 界面索引。在当前账号的已知图片、表情、语音、视频与附件缓存
目录中，按消息记录中的路径、MD5 或资源标识匹配，校验后复制到资料库
`attachments/qq_pc`。不会扫描其它账号或全盘，也不会根据普通同名文件猜测匹配。
找到原图时优先原图；只有缩略图时，阅读器显示“缩略图（原文件尚未找到）”。未匹配的
资源继续标为缺失。缓存内容也参与来源指纹，后来补齐缓存后重新导入即可更新媒体，
即使消息数据库未变化。PC 微信专有媒体恢复尚未接入，原始媒体引用仍保留。
在线下载勾选与上述本地恢复相互独立。

QQ SILK/AMR 语音保留原件，并在转换组件可用且校验通过时生成 WAV 播放副本。
转换失败仍可下载原文件。阅读器提供“下载原始文件”，不会用播放副本替换原始字节。
后续更新保留已恢复原件，原图优先于同一资源的缩略图。

微信 3 部分 LZ4 压缩应用消息正文尚未展开，未知消息和二进制原始字段会保留在
`_desktop_raw`，不会凭空生成文本。未知关键消息表或单一格式消息库解密失败会明确报错，
已经完成的其它来源仍然保留。
